# Conduit Wave 2: evidence and identity recovery

Status: implementation candidate, not independently accepted or installed. Based on
Wave 1 SDK f0a0ed2cf3518db48a517ac76f035c150361079d. Live guardian release stays
disabled; the total provisional release surcharge remains 2 DD, with no live
guardian billing enabled. No key or custodian is provisioned by these tools.

## Flight A — enrollment evidence (A1 format, A2 refusal controls)

`sealed/enrollment.js` exports `verifyEnrollment({policy, evidence, trusted, now})`.
It is an offline verifier, **not** wired into `policyForUse` or guardian release.
Supply trusted pins separately from an applicant's evidence. Never construct the
trusted list by copying issuer keys or deployment hashes out of that evidence.

The policy is the existing version-1 three-guardian policy. Each trusted entry has
`guardian_id`, `issuer_id`, `issuer_key` (public Ed25519 JWK), and
`deployment_sha256` (operator-pinned SHA-256 of the reviewed deployment artifact).
There must be exactly one entry for each guardian, with distinct issuer IDs and
keys. An issuer cannot reuse any guardian encryption, receipt or approval key.

Each signed evidence record has exactly:

```
format: "conduit-guardian-enrollment-v1"
policy_hash, guardian_id, guardian_fingerprint, approval_key_hash
domains: {host, admin, credential, recovery}
deployment_sha256, issued_at, expires_at, issuer_id, signature
```

Hashes and signatures use `sealed/crypto.js` canonical serialization. Sign the
entire record excluding `signature`. Times are integer Unix milliseconds, with
no future issue date, expiration strictly later than checking time, and at most
24 hours of validity. Domain labels must be canonical lowercase ASCII names.
All policy, key, domain, issuer and deployment bindings must match; any malformed,
missing, duplicate, expired or invalid evidence throws. Input is limited to 64 KiB.

Success returns `evidence_verified_live_disabled`, exact policy hash, guardian IDs,
checking/expiry times and `live_guardian_release: false`. This verifies what pinned
issuers signed, not the factual truth of their assertions. Three different keys
or labels can still belong to one administrator. Actual operator-approved issuer
policy, separate control/recovery domains, custodian selection, revocation and
rotation remain prerequisites for a future live implementation. No fixture
result is an independent custody receipt. Clock trust is the caller's responsibility.

## Flight B — endpoint identity recovery (B1 backup, B2 loss/restore controls)

The offline `sealed/backup-cli.js` uses the existing HPKE implementation to encrypt
the endpoint identity to a separately held recovery public key. It signs the
header and ciphertext with the original identity. The recovery private key must
be maintained separately; keeping it beside the endpoint defeats recovery isolation.

No passwords, keys, or new service credentials are accepted on the command line.
All input files must be regular, private, current-user-owned files. Recovery
public and private files have the `publicKey` or identity shapes generated by the
existing crypto API respectively; creating a production recovery authority is an
operator task outside this wave. Public files also require mode 0600 for this tool.

```
node sealed/backup-cli.js export DIRECTORY MAILBOX RECOVERY_PUBLIC_FILE RECOVERY_FINGERPRINT NEW_BACKUP_FILE
node sealed/backup-cli.js restore NEW_DIRECTORY MAILBOX RECOVERY_PRIVATE_FILE ORIGINAL_IDENTITY_FINGERPRINT BACKUP_FILE
```

Verify fingerprints out of band before use. Export requires an existing endpoint
key; it never initializes one. Restore validates signature, recipient, original
pin, mailbox and both private/public key pairs before writing. It uses exclusive
creation, refuses any existing key or symlink and never silently rekeys. Do not
restore into an active endpoint directory. Destination directories/files are
0700/0600. Backups contain public mailbox/key metadata and encrypted private keys;
metadata is not hidden. Outputs contain status and public fingerprints only.

This is **identity backup**, not a full message-history or transport-state backup.
Old ciphertext is recoverable only if its envelope/capsule/release evidence still
exists and the required original identity was backed up. No relay event log,
outbox, idempotency state or guardian journal is rewound. A failed filesystem
write/fsync may leave an incomplete file or an uncertain successful write; the
command reports failure and does not delete or overwrite it. Inspect that fresh
destination before retrying elsewhere. There is no claim of secure deletion of
JavaScript strings from process memory, forward secrecy, or protection from a
compromised endpoint/recovery holder. The API is deliberately absent from MCP so
models are not asked to handle recovery private keys.

## Flight C — regression and independent review

`node --test test/sealed-enrollment.test.js test/sealed-backup.test.js` exercises
the new paths with disposable local identities, including decryption of an actual
pre-loss encrypted message after restore, malformed-but-signed private key pairs,
wrong recovery keys/pins, duplicate restores, symlinks, and CLI execution.

`CONDUIT_TEST_SOURCE=/path/to/reviewed/conduit npm test` runs the complete SDK suite
including relay compatibility. Tests establish fixture/source behavior only.
Independent exact-revision review and its negative probes must precede acceptance.
No installed MCP update, guardian release, real backup creation or provider call
is part of this wave's implementation test run.

Rollback: this candidate adds offline modules/tests/docs only; reverting it does
not alter existing ciphertext or release behavior. Keep the sealed-aware relay
and its append-only history. Never restore the older plaintext-only relay behind
sealed traffic, and never rewind logs to roll back client code.
